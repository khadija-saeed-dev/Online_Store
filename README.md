# Online Store

Monorepo containing the customer storefront, administration app, and Express API.

## Local Development

Install dependencies from the repository root with `npm install`. Copy `backend/.env.example` to `backend/.env` and configure the backend values locally. The example file contains names only; keep real credentials in ignored environment files.

Run these commands from the repository root:

- `npm run dev:backend` starts the API on port 5000.
- `npm run dev:storefront` starts the storefront on port 5173.
- `npm run dev:admin` starts the admin app on port 5174.

The frontend and admin clients use `http://localhost:5000/api` in Vite development. Production builds require `VITE_API_URL`.

## Vercel Projects

Import this same GitHub repository as three separate Vercel projects. Set each project's Root Directory to the folder below and enable access to the repository's root-level workspace files when Vercel prompts for it.

| Project | Root Directory | Framework | Build Command | Output Directory |
| --- | --- | --- | --- | --- |
| Customer frontend | `frontend` | Vite | `npm run build` | `dist` |
| Admin | `admin` | Vite | `npm run build` | `dist` |
| Backend | `backend` | Express (Node.js) | Leave blank | Leave blank |

The backend's default-exported Express app at `backend/src/app.js` is the Vercel function entry point. Vercel handles the production listener; do not configure `PORT` for production. Select Node.js 22.x for all three projects. The frontend and admin `vercel.json` files route client-side page URLs back to `index.html`.

### Environment Variables

Add values in each Vercel project's Settings → Environment Variables. Do not put backend secrets in frontend or admin projects.

Backend project:

- `MONGO_URI`
- `JWT_SECRET`
- `JWT_EXPIRES_IN`
- `CLOUDINARY_CLOUD_NAME`
- `CLOUDINARY_API_KEY`
- `CLOUDINARY_API_SECRET`
- `PUBLIC_SITE_URL`: the customer frontend's production origin.
- `CORS_ALLOWED_ORIGINS`: comma-separated exact customer frontend and admin origins, without paths.

Frontend project:

- `VITE_API_URL`: the backend deployment origin followed by `/api`.
- `VITE_SITE_URL`: the customer frontend's production origin. If omitted, canonical and Open Graph URLs use the browser's current origin.

Admin project:

- `VITE_API_URL`: the backend deployment origin followed by `/api`.

Vite embeds `VITE_*` values into browser assets. Only set public URLs there. API calls in both clients fail clearly at runtime if `VITE_API_URL` is missing in a production build.

### Deployment Order

1. Deploy the backend first with its database, JWT, and Cloudinary settings. The API URL will be needed by both Vite projects.
2. Deploy the customer frontend with `VITE_API_URL`; after its URL is assigned, set `VITE_SITE_URL` to that origin and redeploy.
3. Deploy the admin with `VITE_API_URL` and note its assigned origin.
4. Set backend `CORS_ALLOWED_ORIGINS` to the exact frontend and admin origins, and `PUBLIC_SITE_URL` to the frontend origin; redeploy the backend.
5. Update `frontend/public/robots.txt` with an absolute sitemap directive using the deployed backend URL, for example `<backend-origin>/api/seo/sitemap.xml`, then redeploy the frontend. The sitemap endpoint builds product, category, and canonical URLs from `PUBLIC_SITE_URL`.

Replace these values with the actual URLs Vercel assigns; no production domain is assumed here. Until the backend CORS list is set, browser requests from the deployed sites will be denied.

## Image Uploads

Admin image bytes upload directly to Cloudinary using signed parameters generated by the authenticated backend. The Cloudinary API secret remains backend-only. Cloudinary's public API identifier is returned at runtime for the upload request; it is not embedded in the frontend build and is not a secret. The backend verifies uploaded resource format, size, folder, and secure URL before returning image URLs for product records. The existing local multipart endpoint remains available for compatibility; production admin uploads use the direct signed flow to avoid Vercel's 4.5 MB function request-body limit.

The signed flow keeps the existing 5 MB per-image, 8-image batch, JPG/JPEG/PNG/WEBP, and `online_store/products` folder constraints. Vercel's request limit applies to requests sent to the function, not the separate browser-to-Cloudinary file transfer.

The backend currently exposes authentication and product routes. An `Order` model exists, but no order routes or order API are currently registered.
